# Build Tasks

Everything needed to build the tool described in `PROJECT_DEFINITION.md`, informed by the software/config inventory in `PLATFORM_EQUIVALENTS.md`. Ordered so each phase can be built and tested on top of a working previous phase.

Every task includes a **Tests** line. Where a task is pure logic (parsing, validation, state transitions, diffing), the tests are real unit tests with fixtures/mocks. Where a task inherently touches the live OS (actually installing a package, an elevation prompt, real GUI rendering), the unit-testable slice is called out explicitly and the rest is marked **integration/manual** — claiming a unit test for something that requires a real OS mutation would be misleading, so those are flagged rather than glossed over.

Remaining open decisions this task list assumes a default for (see memory / prior discussion) are marked **(assumed, confirm before starting)**.

**Hard rule, not a preference**: Phase 1 (the engine — catalog, diagnostics, plan/diff, history, profiles, overlay repos) has zero dependency on whichever TUI library Phase 2 ends up using. The engine must be fully usable and testable — including from `--yes`/`--dry-run` — with no TUI involved at all. This is what lets the terminal interface be swapped later without touching how the tool actually decides what to do.

**File format rule, not a preference**: TOML for everything that's configuration or metadata — `meta.toml`, `profiles/*.toml`, `identity.toml`, the user config file, manifest exports — never for anything that gets executed. Shell scripts (`.sh`) for every one of the four operations (`detect`/`install`/`remove`/`update`) — never folded into a declarative TOML shortcut, even for a trivial one-line change — so any single operation can always be run standalone, by hand, without going through the engine at all.

### Correctness audit — 2026-09-01, verified against the files (not from notes)

**FIXED 2026-09-01 — the `update` operation now works end-to-end.** What follows is the original finding, kept for the record; the fix is described after it.

**The `update` operation was inert end-to-end — the tool could not update anything it had installed.** Verified by reading every script and by running the real plan engine:
- **No `detect.sh` in the catalog ever exits 2** (`needs-update`) — every one returns only 0/1, so that state is never produced.
- **Zero `update.sh` files exist** across all 28 entries, on any platform.
- Consequently `computePlan` can never emit an `update` action: a selected entry that is already installed resolves to `satisfied` and is dropped as `already-satisfied` (confirmed by running it — 0 actions, skipped `already-satisfied`).
- The engine side is correct and not at fault: `OPERATIONS` includes `update`, `ActionKind` includes `"update"`, and the documented missing-`update.sh` fallback (`ops.update ?? ops.install`) is implemented and works — feeding it a synthetic `needs-update` state does produce `update via linux/install.sh`. The gap is entirely in catalog content.
- Knock-on effect: the TUI's `↑ update available` glyph and its legend document a state that can never occur.

**The fix.** Every `detect.sh` for a package-manager-backed entry now implements the full documented contract — 0 = installed and current, 1 = not installed, **2 = update available** — instead of only ever returning 0/1. 73 of 83 platform-entries regenerated, covering apt/deb (installed version vs `apt-cache policy` candidate), flatpak (deployed commit vs cached remote commit), Homebrew (`brew outdated`), winget (`winget upgrade --id`), and AppImage via Gear Lever's own `--list-updates`. Each check is offline-safe: when the newer version can't be determined it reports "current" rather than inventing an update. The remaining 10 are `script`/`direct-download` entries (Go, Rust, Volta, Claude Code, AWS CLI, JetBrains Toolbox, Helium on Windows) whose upstreams have no uniform version query — deliberately left reporting "installed" rather than guessing.

No `update.sh` files were added: the documented fallback (`ops.update ?? ops.install`) is implemented and correct, and for every one of these methods re-running the install *is* the update.

**Verified against real state, not just inferred**: in a container, `git` pinned to `1:2.43.0-1ubuntu7` with candidate `1:2.43.0-1ubuntu7.3` made `detect.sh` exit **2**; upgrading to the candidate made it exit **0**; with git absent it exits **1**. Feeding that state to the real plan engine produced `actionKind: update` and rendered `update Git (requires elevated access)` — the path that was previously unreachable. Two regression tests in `src/catalog/bundled.test.ts` now fail if any package-manager entry loses its exit-2 path or its exit-code documentation, since this capability died silently once already.

**Verified correct** (each checked directly, not assumed): every platform directory has all three of detect/install/remove; every script using `sudo` declares `requiresElevation` for that platform, and nothing declares it without using `sudo`; install/remove identifiers match for winget, Homebrew and Flatpak across every entry; every `install`-kind entry has the required `website`; declared `installMethod` matches what each script actually does for all 28 entries (three apparent mismatches were false positives from the detection heuristic and were confirmed correct by reading the scripts); the meta parser genuinely rejects unknown fields, invalid `installMethod` values, wrong-typed `requiresElevation` and a missing `name`.

**Smaller real defects found**:
- **FIXED**: `proton-mail` and `proton-pass` (linux) built a temp path with `mktemp -u` — a name is reserved but the file isn't created, which is race-prone — and clean up with a trailing `rm -f` rather than a `trap`, so a mid-script failure leaves the downloaded `.deb` behind. Both now use a real `mktemp -d` with a `trap` cleanup, and run `apt update` before installing the local `.deb` so dependency resolution no longer depends on the machine's lists already being fresh.
- **FIXED**: `src/elevation/session.test.ts`'s "a rejected call doesn't throw" asserted nothing and passed purely by not throwing, so it could not distinguish a working implementation from one that skipped the call entirely. It now asserts both that the rejection is swallowed and that the real `sudo -k` was attempted.
- ~~No entry sets `destructive`, so the plan's destructive flagging and the detail pane's red warning are untriggerable today.~~ **Fixed.** The cleanup kind was retired rather than filled, so waiting for it left the warning permanently dead — a review caught that the `[DESTRUCTIVE — hard to reverse]` marker could never appear. `computePlan` now defaults a `remove` action to destructive instead of relying on each entry to declare it (`entry.meta.destructive ?? true`), which is also the honest default under desired-state selection: unchecking a box is what triggers a removal. An entry can still set `destructive` explicitly to be flagged on install too. 3 tests in `src/plan/compute.test.ts`; verified end to end by rendering a real plan (`remove LibreOffice … [DESTRUCTIVE — hard to reverse]`).

### Robustness pass — 2026-09-01 ("prepare the tool for things that could go wrong")

Four real failure modes, each found by inspecting the code rather than guessing, and each verified:

1. **Nothing bounded script execution.** `runScript` supported `timeoutMs` but **no caller ever passed one** — every detect and every install ran unbounded, so a script waiting on input or a dead socket froze the app with no way out. Detect scripts now get 60s (they are quick checks by design, and one hung probe would stall startup before the UI is usable); plan actions get 30 minutes (installs genuinely take minutes; the point is a bound, not a short one).
2. **The timeout wasn't actually a timeout.** Even when one fired, the code then awaited `child.output()`, which only resolves once *every* holder of the piped stdout/stderr exits — so a descendant surviving the kill (the elevated path has no process group to kill) turned a bounded timeout into a permanent hang. It now stops waiting on that pipe and returns. Verified by a test that survives a backgrounded `sleep 30`: the call returns in ~500ms against a 500ms timeout. The earlier claim that this path "cannot cut the run short" was wrong and the misleading test that asserted it has been replaced.
3. **The sudo session leaked on failure.** `keepAlive.stop()` and `releaseSudoAccess` ran sequentially after execution, so a throw skipped both — leaving a repeating background `sudo -n true` timer for the rest of the session and the user's cached credential alive well past the run that needed it. Both the TUI and the `--yes` path now release in a `finally`.
4. **The terminal could be left wrecked.** Restoration is now centralised in `src/tui/terminal.ts` (mouse reporting off, cursor shown, alt-screen exited), invoked from an uncaught-`error` handler and from a `finally` around `waitUntilExit`, in addition to the existing unhandled-rejection net.

**Measured limitation, not assumed**: terminal restoration **cannot** be driven from a signal handler while Ink holds raw mode. A control experiment settled it — `Deno.addSignalListener("SIGTERM", …)` fires reliably in a plain script, and never fires once Ink enables raw mode (the same interaction that breaks SIGWINCH, see App.tsx's resize polling). So an external `kill` still leaves the terminal dirty and needs `reset`. Ctrl+C is unaffected, because Ink reads it from stdin itself rather than relying on a signal. This is documented in `terminal.ts` rather than papered over with a handler that would never run.

### Floating-promise audit — 2026-09-01 (user's catch)

**"The way we have async function inside useEffect could cause issues if the promise rejects — no one to capture it."** Correct, and it mattered more here than in a typical React app: an unhandled rejection while Ink holds stdin in raw mode kills the process *without* running Ink's cleanup, leaving the terminal full of garbage, beeping on mouse movement and unresponsive to Ctrl+C. This project already shipped exactly that crash once, from a history write that threw.

Audited every async operation started from a synchronous context. Three were genuinely unprotected:

- **The startup effect** — `detectCurrentOS`, `runPreflight`, `materializeAssetDir`, `bootstrapCatalog`, the diagnostic scan and the catalog-key cache write were all inside a bare `(async () => { … })()`. A throw from any of them (an unreadable catalog directory, a full disk during asset extraction) went straight to an unhandled rejection.
- **`runPlan`**, invoked as `onConfirm={() => runPlan(plan)}` — and it *can* now throw, since the elevation release was moved into a `finally` that rethrows. Dropping that promise meant a mid-run failure both crashed the process and stranded the UI on the progress screen forever.
- **The done-screen dismiss handler**, which re-runs diagnostics.

All now go through a `guard(context, task, onFailure?)` helper that cannot let a rejection escape: it reports into the status line *and* the notices screen, and can restore screen state (a failed run returns to browse rather than freezing on progress). `main.tsx`'s last-resort `unhandledrejection` net stays, but it is only a net — it stops the crash without being able to explain what failed or put the UI right.

**Verified by injecting a real failure** into the startup path rather than reasoning about it: the app rendered `startup failed — injected startup failure · 1 notice(s) — press n` and stayed fully usable, where previously it would have died with a wrecked terminal.

### Library adoption — 2026-09-01 ("could all this code be simpler if we use some libraries?")

Assessed against the actual code rather than by instinct, and adopted in the two places that measurably paid off.

**Zod for the four TOML parsers** (`catalog/loader.ts`, `config/store.ts`, `profiles/store.ts`, `manifest/store.ts`). These were **872 lines containing 37 hand-written `throw new Error` calls** doing field-presence, type and allowed-value checks — textbook schema validation written by hand, with the TypeScript interfaces maintained separately from the code that enforced them.

Result: **872 → 391 lines** (plus a 68-line shared helper), a **413-line net reduction**, and hand-written throws down from **37 → 2**. The two that remain encode genuine rules a schema can't express: TOML syntax failure (reported distinctly, since the fix differs from a schema failure) and "website is required for install-kind entries", which depends on the entry's kind — information the document itself doesn't carry.

The migration deliberately preserved error-message quality, which was the main risk. `formatIssues` rebuilds this project's established `"field.path": what went wrong` shape from Zod's issue list, and `strictTable` overrides Zod's default wrong-type text so it says **"must be a table"** rather than "expected object" — every document here is hand-edited TOML, where *table* is the correct term and "object" describes a JavaScript value the author never wrote. That regression was caught by an existing test, which is exactly why the whole migration was done against an unchanged test suite: **all 360 tests pass with no assertion edited**.

**ink-text-input for the two text fields** (search box, profile picker). Both had hand-rolled character handling that required `input.length === 1` and therefore silently dropped every multi-character chunk — i.e. fast typing and *all* pasting, which is precisely how a profile URL gets entered. This was the same bug found twice. Verified compatible before adopting (peer deps `ink >=5`/`react >=18` against our ink 7/react 19) and verified working under a real pty, distinguishing genuine rendering from terminal echo: the component renders `query: proton mail` on its own line after a multi-character burst. Both fields also gain cursor movement and mid-string editing, which the hand-rolled versions never had.

**Deliberately not adopted**, with reasons: `execa`/`tree-kill` for process execution (the runner's complexity is `setsid` process-group semantics traded against sudo's tty-keyed credential cache and SIGTTIN — not something a general-purpose library models, and `tree-kill` hasn't been published since 2019); `ink-select-input` for the checkbox list (no category grouping, status glyphs, viewport windowing or checkbox-vs-row click discrimination — we would keep our logic *and* inherit a dependency); `neverthrow` (the `guard` helper is 8 lines and already solves it); XState (7 states with simple transitions doesn't pay for itself).

Worth recording honestly: almost none of the bugs found in this project were the kind libraries prevent — sudo's tty-keyed credentials, `deno compile`'s virtual filesystem, Gear Lever's lowercase filenames, `apt` taking Steam as collateral, signal handlers dying under raw mode. Those were environment problems, and a library layer would have made several *harder* to diagnose. Every npm dependency also carries real risk here: `blessed` crashed outright under Deno, and `ink-mouse` is unreliable in Ghostty with no API to scope its escape sequences.

### Duplication review — 2026-09-01 ("is there any redundant code?" / "is that truly useless?")

Measured rather than assumed. The catalog contains ~600 lines that look redundant: an 18-line apt collateral-removal guard copy-pasted into 15 `remove.sh` files, 78 winget scripts identical but for the package ID, 15 apt detect scripts likewise, and 18 byte-identical files (git-identity's three platforms are literally the same file three times).

**Conclusion after examining it properly: most of this should stay.** The duplication is buying things that are actual requirements, not laziness:

- **Standalone-runnability.** Every operation is a file you can copy to a machine and run by hand — a property that has repeatedly made debugging possible here. `source ../../_shared/apt-remove.sh` breaks it.
- **Overlay independence.** Overlays override whole platform folders (§1.9). A core script sourcing a shared path would couple someone's personal repo to the core catalog's internal layout.
- **Freedom to diverge.** 6 of the 15 apt removes *already* differ around the guard, adding repo/keyring cleanup. A shared helper would grow flags to absorb that, and the flags would be worse than the copies.
- **Auditability.** For a tool that runs with sudo, one self-contained file is easier to review than an include chain.

The winget/brew one-liners are not really duplication at all — a package identifier plus two lines of syntax, with no logic to centralise.

**What duplication genuinely costs is silent drift**: a fix applied to one copy and not the other fourteen. That is bought back with a test rather than an abstraction — `bundled.test.ts` now extracts the guard from every apt-based `remove.sh` and asserts all copies are byte-identical, naming the count and telling the fixer to apply the change everywhere. Verified non-vacuous by drifting one copy and watching it fail. All 15 are currently identical.

**In `src/` there is no meaningful duplication left** — the Zod migration removed the last large block. `App.tsx` at 875 lines (28 top-level concerns, 19 `useState` hooks) is *under-decomposed* rather than duplicated; splitting it is a separate, lower-value cleanup with real regression risk given how much of it is now load-bearing.

### Desired-state selection model — 2026-09-02 (user's design change)

**The checkbox now means "this should be on my machine", not "perform this action".** Previously a deselected entry was skipped *"entirely, no exceptions"* — unchecking something did nothing at all, and removing software required selecting a separate `cleanup`-kind entry. Now `computePlan` plans **both directions**: a selected entry that is absent is applied, and a deselected entry that is present is undone.

This supersedes the §1.5 decision that deselection never triggers a reversal. It is a better model — one mental model instead of two, no inverted semantics to explain, and preinstalled bloat simply shows up checked so you uncheck it — but it makes deselection destructive, which drove three supporting changes:

1. **First-run seeding, which is what makes it safe.** Measured against the real catalog: with an *empty* selection and four entries installed, the planner produces **four removals**. That is the failure mode — on a fresh machine the saved selection is empty while the machine is full of software. So when no saved selection exists, everything currently present starts checked; the same scenario then plans **zero actions, four skipped**. Later runs deliberately do **not** re-seed: re-adding whatever happens to be installed would silently undo an intentional uncheck. Anything installed outside the tool since last run is surfaced by the reconciliation notice instead.
2. **The deselect-all binding is gone.** `N` used to clear a to-do list; under desired-state semantics one keystroke would queue the removal of every visible entry. `a` (select-all) is retained — its worst case is installing too much, which the confirm screen shows before anything runs.
3. **`remove` is planned uniformly for every kind**, with no special-casing, because each kind already defines its own `remove.sh` as "undo `install.sh`" — for a cleanup entry that means reinstalling the app. Covered by a test.

**A stale test that was passing for the wrong reason** was found here: `"a deselected-but-installed entry produces no action"` still passed after the change, only because the test fixture had no `remove` script for the planner to find. The fixture now carries one (as every real entry does), and the test asserts the new behaviour; three more cover the already-absent case, the missing-remove-script case, and cleanup inversion.

**A real bug found during verification**: the first-run notice was appended with `setNotices`, then silently overwritten moments later by the single `setNotices(collected)` assignment — so it never reached the screen. Notices are now built as one list and set once. Verified end to end in the container: a first run pre-selects the 9 installed entries, reports *"First run: 9 already-installed entries were pre-selected, so nothing is removed unless you uncheck it"*, and pressing Enter says **"Nothing to do"** with no removal planned.

### `cleanup` kind retired for debloat — 2026-09-02

Following directly from the desired-state change above, the seven debloat entries were converted from `cleanup`-kind to ordinary `install`-kind entries. A preinstalled app is now simply an entry that starts checked because it is present; unchecking it removes it. Rhythmbox plans as `Already satisfied, no action needed` when checked and `remove Rhythmbox (requires elevated access)` when unchecked — no special kind, no inverted semantics, one mental model.

The conversion was mechanical (`install.sh` and `remove.sh` swap roles, `detect.sh` un-inverts so 0 means present) plus two additions: a `website`, which the schema requires for install-kind entries and which was verified to resolve for all seven rather than guessed, and the standard exit-2 update check that every apt entry carries — so these apps now participate in update detection too, which they could not as cleanup entries.

**The catalog now has zero `cleanup` entries.** The kind still exists in the schema and the engine, and `computePlan` still handles it (a test covers the inversion), but nothing uses it. Worth deciding later whether it earns its place: with desired state, "remove this software" is just an unchecked install entry, and "disable telemetry" is a `configure` entry. Removing the kind would touch the schema, validator, `labelFor`, PROJECT_DEFINITION §2 and several tests, so it is not worth doing on a hunch — but it is now dead weight rather than a load-bearing concept.

**A test that needed refining rather than weakening**: the guard-drift test began failing because two *legitimate* guard variants now exist — the plain one (any collateral aborts) and the family-prefix one (the app's own subpackages are expected). It now groups by variant and asserts each is internally consistent. Fixing it also exposed a flaw in the test itself: the guard was extracted by anchoring on a comment that only the plain variant carries, so every family-variant script silently yielded the same empty slice and would never have been compared at all. It now anchors on the `COLLATERAL=` assignment and asserts the extraction succeeded, and was re-verified to catch a deliberate drift.

### Selection-model migration — 2026-09-02 (**user-reported bug**: "I only selected OrcaSlicer, the list of changes had 41 items")

**The worst bug found in this project so far, and it was found by the user on a real machine.** A run that checked one entry proposed **41 actions**: one install and forty removals.

**Cause.** The desired-state change altered what `selectedKeys` *means*. Under the old model it was a queue of things to install, so a config listing six entries meant "install these six". Under the new model the same six mean "these six, and nothing else, belong on this machine" — turning every other installed entry into a planned removal. The user's config was written under the old model, on 2026-08-31, and held exactly six keys.

**Why the existing safeguard missed it.** First-run seeding was built precisely to stop an empty selection reading as "remove everything", but it triggers only when `selectedKeys` is *empty*. A pre-migration config is not empty, so it sailed straight past the guard. The safeguard was written for new machines and never considered existing configs — a migration that changes the meaning of stored data needs a version marker, not a value check.

**The fix.** `src/config/migrate.ts` adds `selectionModel` to the config; its **absence** is the migration signal. `resolveInitialSelection` handles three cases in one tested function: an already-marked config is authoritative (deselection keeps working); an empty one seeds from live state; an **unmarked, non-empty** one is unioned with what is installed. The union is the only reading that cannot destroy anything — the old keys said what the user wanted present and said nothing whatever about what they wanted removed. The marker is written to disk *before* the selection is set, so the persistence effect cannot race it into saving an unmarked config and re-migrating forever. The notices screen explains what happened and how many entries were kept.

**Verified** by reproducing the user's exact config in the container: previously 41 actions, now **1 action (install OrcaSlicer) and zero removals**, with `git` and `curl` auto-checked and `selectionModel = "desired-state"` written back. 6 unit tests, including one that asserts deselection still works after migration, so the fix cannot over-correct into "removal is impossible".

**The lesson worth keeping**: the desired-state change was reviewed, tested and documented, and still shipped a defect that would have uninstalled forty things — because every test and every sandbox run started from either a fresh config or a config the new code had written itself. No test ever started from *old data*. Changing the meaning of persisted data is a migration, and migrations need their own tests.

### Three more user-reported items — 2026-09-02

**1. "No need to show what is already applied, too much noise, only show what will change."** `renderPlan` listed every already-satisfied entry, and (briefly) every available update, alongside the actions. ### Cursor moves over rows, not items — 2026-09-02 (user: "I should be able to select the section name to press space and install all")

### Emoji, applied under an enforced safety rule — 2026-09-02

The question asked first was whether emoji are safe here. Measured rather than assumed: Ink lays out with `string-width`, which reports **2 columns for every emoji form** — plain, VS16, ZWJ, flag, skin tone alike. Terminals only agree with that for a **single East-Asian-Wide code point**. Sequences break it: a ZWJ pair renders as two emoji (4 columns) without ligature support, flags as two regional-indicator boxes, skin tones as base + swatch, and a VS16 emoji sits on a *narrow* base so a terminal ignoring the selector draws 1 column where the layout reserved 2.

That matters more here than in most TUIs: the list draws exactly one screen row per entry and the viewport math depends on it, so a row wider than computed wraps and the pane renders more lines than it has — the same failure that once pushed the whole interface off screen.

`src/tui/glyphs.ts` therefore holds every non-ASCII glyph the UI draws, with `isSafeTerminalEmoji` encoding the rule (one code point; in the emoji planes, or one of the older BMP symbols that are `Emoji_Presentation=Yes` and Wide). A test asserts **every glyph in every group** satisfies it, so a new icon cannot regress the layout. It caught two during this pass: `⚙️` and `⏭️` are two code points on narrow bases, replaced with `🔩` and `⏩`; `🕶`/`🛡`/`👁`/`⚠` were rejected the same way.

Applied: category icons on header rows, an emoji checkbox (`✅`/`⬜`/`🟨` — all exactly two columns, so rows cannot ripple as you select), outcome markers shared by the progress view, run summary, history and pre-flight, and pane titles.

**Deliberately not applied to the scrollbar.** No emoji is narrow, so a bar built from them would be a two-column stripe of separated glyphs rather than a continuous line. The box-drawing characters stay. Worth recording that `┃ │ · — ● ↑` are East-Asian **Ambiguous**: `string-width` counts them as 1, but a terminal configured for CJK ambiguous-wide renders 2. That is a pre-existing latent risk in the frame and scrollbar, unrelated to emoji, and unaddressed.

The checkbox change moved hit-testing from three columns to two; `CHECKBOX_GLYPH_WIDTH` is now re-exported from the glyph module so the mouse geometry cannot disagree with what is drawn, and the two click tests that encoded the old width failed exactly as they should have.

### "No internet access" on a machine that plainly had it — 2026-09-02 (user-reported)

Four icons were replaced (🥷→🔐, 🧊→📐, 🧰→🔌, 🟨→🔶), and `ai` moved 🤖→🔮 because the range is deliberately conservative in both directions — it also rejects a few genuinely old emoji that happen to live in the U+1F900 block. That costs an icon choice; the opposite error costs a broken row on someone else's machine.

Rows also now `wrap="truncate"` and the scrollbar column is pinned at `width={1}`, so a row wider than the pane can never grow the row box and push the border sideways. Measured across scroll positions at 90 columns: every rendered row, category and item alike, is exactly 90 display columns wide.

**Two corrections to my own findings during this pass, both from bad measurement rather than bad code.**
- I concluded the interface was *unresponsive during a scan* — pressing `n` appeared to do nothing. It was the capture harness, not the app: checking the raw byte stream immediately after the keypress shows `🔔 Notices` rendering while `diagnosing` is still on screen. The interface is responsive throughout. A minimal Ink + subprocess probe confirmed independently that Ink receives keys while spawning children.
- Measuring row alignment by *character count* showed a one-column difference between category and item rows. That was the metric: a wide emoji is one character occupying two columns. By display width the rows are identical.

One genuine change did come out of the false lead: scripts no longer inherit the interface's stdin (`stdin: "null"`, except when `preserveControllingTerminal` keeps the tty for `sudo`). It is correct hygiene — a script that reads stdin would otherwise eat the user's keystrokes — but it fixed no demonstrated bug and should not be described as having done so.

### Why so many entries failed — 2026-09-03 (user-reported, diagnosed from their run history)

The user's `history.jsonl` held **22 failures across 31 recorded actions**. Not many causes — two, and one accounts for almost all of it.

**18 of 22: every flatpak entry, all with `No remote chosen to resolve matches for <app>`.** The message reads like a missing remote and is the opposite: flathub was configured in *two installations* (Zorin OS ships a system-wide flathub, and there was a per-user one as well), so an unscoped `flatpak install` had no way to choose. Interactively flatpak asks; under `--noninteractive` it fails. The catalog named the remote in three scripts and omitted it in the rest — but naming the remote was never enough, because the ambiguity is between *installations*, not remotes. GearLever's script did name `flathub` and failed identically, which is what pointed at the real cause.

Confirmed directly on the affected machine, read-only:

```
flatpak remote-info --cached flathub org.gimp.GIMP            → Remote 'flathub' found in multiple installations
flatpak remote-info --system --cached flathub org.gimp.GIMP   → 84c286d8a8d3957253b71923c2e15b65…
```

All 36 flatpak entries (102 scripts) rewritten so every `install`/`uninstall`/`remote-info` names its installation: detect resolves the scope before querying, install targets `--user` (no root, cannot collide with distribution-managed system apps) and adds the user remote with `--if-not-exists`, and remove uninstalls from whichever installation actually holds the app. A convention test now rejects any unscoped flatpak command, so this cannot come back.

**The other 4: all terraform, all on 2026-08-31, none since.** They are the failures that drove earlier fixes and each has a matching one: `sudo: a terminal is required` (fixed by keeping the controlling terminal for elevated scripts), `gpg: dearmoring failed: File exists` (fixed by writing the dearmoured key to stdout instead of `-o`), `gpg: can't create '35;49;45M…'` — mouse-tracking escape sequences injected into the prompt (fixed by disabling mouse reporting around elevation), and one transient `Failed to fetch` from an Ubuntu mirror. Terraform has not been retried since; it is still not installed on that machine, so the fixes remain unproven there.

Worth stating plainly: the tool reported all of this accurately and never pretended to have succeeded. What it lacked was any way to notice that eighteen failures shared one cause — which is what a run history is for, and why reading it was the first step rather than guessing.

### The test harness leaked 119 containers — 2026-09-03 (user-reported)

The user found **119 leftover `deno` + `conmon` processes** holding 3.2 GB RSS and 12.4 GB of swap, and killed them by hand: *"don't let that happen again."*

Entirely a harness defect, not the tool's. Every sandbox test ran `podman run --rm -i -t` under `pty.fork()` and then `os.kill(pid, SIGKILL)` on the **podman client**. SIGKILL cannot be trapped, so podman never tore the container down — `--rm` never fired — and the container, with a `deno` process inside it, kept running. One leaked container per test run, silently, across days of testing.

Replaced with `sandbox.py`, which enforces what should never have been left to memory:
- every container gets an explicit `--name autoinstall-test-*`, so it can be removed even when the client is gone;
- teardown is `podman rm -f <name>` inside a `finally`, *before* reaping the client, plus an `atexit` sweep for anything an earlier crash left behind.

Verified to leave zero containers after a normal run **and** after a run that raises partway through. The 17 older harnesses were moved to `.leaky-retired/` so they cannot be picked up and reused. Recorded as a standing rule in the project memory, since it outlives this session.

The lesson generalises past podman: a test that starts something outside the process must own stopping it, and `--rm` is not ownership when the supervising client can be killed. Checking `podman ps -aq` after a test session costs nothing and would have caught this on day one.

### Steam was reported absent on a machine that had it — 2026-09-03 (user-reported)

### One program, two packagings, two entries — 2026-09-03 (user's design call)

*"For things like steam, we should show steam-flatpak and steam-deb etc. in the list, so the user can install/remove it."* This replaces the fix from earlier the same day, which was worse: making Steam's single entry recognise both packagings meant it could detect two things but only ever remove one, and it had no way to express *"remove the Flatpak, keep the deb"*. That is not hypothetical — the reporting machine had **VSCodium and Signal each installed twice over**, apt and Flathub at once, and the tool could neither show nor undo the duplication.

Three programs are now split, each into a `-deb` and a `-flatpak` entry: **Steam, VSCodium, Signal**. Each variant detects, installs and removes only its own packaging, and names it in the display name (`Steam (deb)`, `Steam (Flatpak)`) so the two are distinguishable in a list.

**The split is Linux-only, which the layout already handles.** The base entry keeps its macOS and Windows folders and loses its Linux one, so on Linux it filters out of the list entirely (`entriesForPlatform`) and only the two variants show, while macOS and Windows still see one entry. No mechanism was needed for this — it falls out of "a missing platform folder means not applicable here".

Notes carry the trade-off rather than hiding it: the deb is not sandboxed and reaches system graphics drivers directly (usually better for Steam); the Flatpak is sandboxed and needs Flatseal to reach outside it. Signal's Flatpak entry states plainly that Flathub reports `verified=false` for it — it is community-maintained, not published by Signal — and exists mainly so a machine that already has it can remove it.

Verified against the reporting machine, all six variants matching ground truth exactly: `steam-deb` installed / `steam-flatpak` not; both VSCodium variants installed; both Signal variants installed. A new convention test pins the invariants — each variant is Linux-only, names its packaging in parentheses, and the base entry must not also apply to Linux (which would list the same software twice).

**One consequence to be aware of:** the ids `gaming/install/steam`, `dev-tools/install/vscodium` and `communication/install/signal` no longer exist on Linux, so a saved selection naming them reports "previously selected entry no longer in catalog" on the notices screen. That path already existed and degrades gracefully, but the entries do need re-selecting once.

Catalog is now 92 entries (79 Linux, 58 macOS, 55 Windows).

### Full project review before release — 2026-09-03

Reviewed against a release bar rather than a feature bar: not "does it work on the machine it was written on" but "what happens to someone who installs this". **513 tests, check/lint/fmt clean, binary compiles and runs.** Four defects found, all fixed; two blockers remain and neither is code.

**1. `--yes` bypassed every selection safeguard. The most serious defect in the project.** The CLI read `config.selectedKeys` raw, skipping first-run seeding, the desired-state migration and new-entry seeding alike. Demonstrated with the compiled binary against real configs:
- Empty config → would have proposed removing **all 53 installed entries**, unattended, with no prompt.
- Pre-migration config → would have removed **52**.

Both now resolve through the same `resolveInitialSelection` the interactive app uses, and print what they inferred. Deliberately *not* persisted: `--dry-run` must touch nothing, and an unattended run writing a reinterpreted selection back would make a one-off invocation permanent. The unattended path is the one place nobody is watching, which makes it the last place that should have skipped the safeguards.

**2. Every catalog update proposed removing newly-added software.** Adding Grayjay, Minder and the power profile made the next run offer to uninstall all three from the machine they were written on — they were unchecked (never shown to the user) and installed (already there), which reads as "remove". Entries the catalog has only just gained are now seeded from live state, exactly as a first run seeds everything: silence about an entry you have never been offered is not a decision. Verified with the rebuilt binary — three destructive actions became "Nothing to do", with a note.

**3. The release never stamped a version.** `TOOL_VERSION` was a hardcoded `"0.1.0"`, so every release would have reported 0.1.0 and the built-in update check would have told every user of every later release they were out of date — permanently, and wrongly. **4. Also: the README screenshot had drifted to `[1 of 79]` against 90 Linux entries, because the accuracy test only pinned the prose. It now pins every count in the README, verified by making it fail on purpose. And 281 of 688 catalog scripts had lost their executable bit — harmless to the engine, which runs `bash <path>`, but the design rests on any operation being runnable by hand, and `./detect.sh` failing with "permission denied" is a pointless obstacle exactly when someone is debugging. ### CI review before release — 2026-09-03 (user's question: "is the github actions ready? will that collect logs?")

`ci.yml` was ready. `catalog-lifecycle.yml` — the workflow that exists specifically to close the macOS/Windows verification gap — **was not, and would not have produced usable evidence.** Five defects:

1. **The weekly run exercised one entry.** `ENTRIES` defaulted to `dev-tools/install/jq`, so the scheduled job that is supposed to verify 70 macOS and 69 Windows entries tested exactly one, on all three platforms. Now defaults to `all`.
2. **Nothing was collected.** No artifacts, no job summary — output went to the Actions console log only, which expires and is awkward to compare between weeks. Now writes a per-entry log file, uploads them as an artifact (`if: always()`, since a failure is precisely when they are worth keeping, 90-day retention), and emits a markdown results table to the job summary.
3. **A declined removal counted as failure.** `remove.sh` exits **3** when the collateral guard refuses to take unrelated packages with it — a correct, protective outcome. The workflow treated any non-zero exit as a failure, so the guard working as designed would have shown as a red build.
4. **A failed removal could pass silently.** The post-removal check was `[ "$gone" -eq 0 ]`, but `detect` returns **2** for "present but outdated". An entry that removal left behind in that state reported success. Reproduced with a deliberately broken fixture: the old check passed it, the new one catches it — `still reports present after removal (detect=2)`.
5. **`aarch64-pc-windows-msvc` was released but never compile-checked**, so a break in that target would first have appeared during a release build. CI and release matrices now match exactly, asserted by comparing the two files.

Also added: the lifecycle **skips an entry already present on the runner** rather than counting it as a pass. Exercising it would have removed software the runner image shipped, and proved nothing — the install step has nothing to install. Verified locally, where it correctly refused to touch an installed `jq`.

The logic moved out of the YAML into `scripts/lifecycle.sh`, so it can be read, syntax-checked and run by hand against a VM — the same property every catalog script has, for the same reason. Both paths verified in the container against purpose-built fixtures: a well-behaved entry passes, an entry whose removal silently does nothing fails.

The `binary` job now also asserts that a dry-run on a **clean** runner proposes no removals, which is a direct regression test for first-run seeding — the failure that would have uninstalled 53 programs unattended.

### Cross-platform equivalents audit — 2026-09-03 (user's question)

*"Check if it is possible to add other platform equivalent options."* A different question from "should every app exist everywhere": this is about *different software doing the same job*, the way Solaar and Logi Options+ already share one entry. Audited every entry missing a platform and split them by whether the **behaviour** transfers.

**Four gained a real counterpart:**

- **`finder-tweaks` → `file-manager-tweaks`.** The behaviour — show hidden files, show extensions, prefer a list view — was never macOS-specific; only the application was. Now covers Nautilus via gsettings and File Explorer via its HKCU settings. Renamed because an id naming one platform's file manager was the reason nobody noticed the other two were missing. Linux has no extensions toggle to set: it never hides them.
- **`power-profile` → Windows.** `powercfg /setactive` with the High performance GUID, duplicating the scheme first so it works on machines where the manufacturer's power slider hides it. **macOS deliberately omitted**: Apple Silicon offers Low Power Mode as a toggle, not a performance profile, so there is nothing equivalent to switch on.
- **`automatic-updates` → Windows.** The interesting half is the reversal: Windows updates automatically out of the box, so the entry's job is to *undo* a policy that turned it off. Unchecking it therefore **deletes that policy** rather than setting `NoAutoUpdate=1` — unchecking a security entry must never leave the machine less safe than it was found.
- **`system-limits` → macOS.** Only the open-file half applies, since macOS has no inotify. Installed as a LaunchDaemon rather than a bare `launchctl limit`, which does not survive a reboot — an entry whose effect quietly disappears overnight is worse than one that never applied. Removal says plainly that the raised limit persists until the next reboot, because `launchctl` cannot lower it in place.

**Assessed and correctly left alone**, each for a reason rather than for lack of time:
- `suggested-content` (Windows only) — neither GNOME nor macOS advertises applications in its menus, so there is no behaviour to port.
- `dock-autohide` (no Linux) — GNOME, Zorin and KDE each ship a different dock; `dash-to-dock`'s schema is not even installed on the reference machine.
- `tracker-blocking` (no Windows) — its hosts file needs an elevated shell, and Windows elevation is still unsolved.
- `encrypted-dns` (no macOS) — needs a signed configuration profile.
- `background-services` (no macOS) — launchd agents are SIP-protected.
- The Linux-only **flatpak and GNOME tooling** (Flatseal, Gear Lever, Warehouse, Bazaar, Extension Manager, DistroShelf) and the WINE managers (Bottles, Lutris) have no counterpart because the concepts they manage do not exist elsewhere.
- `ssh-hardening` on Windows would mean editing `%ProgramData%\ssh\sshd_config` for an optional server component most machines never enable — a genuine gap, but one worth doing deliberately rather than in a sweep.

**Catalog: 134 entries — 91 Linux, 71 macOS, 96 Windows.**

### Everything installed on the reference machine is now catalogued — 2026-09-03 (user's request)

Listed what was actually installed and added all of it: **23 new entries**, taking the catalog to **157 entries — 114 Linux, 78 macOS, 100 Windows.** Every identifier was verified against Flathub, the Homebrew API or the winget manifest repository before being written, and every new entry's `detect.sh` was then run against the real machine — 23 of 23 report correctly.

Equivalents were added wherever they genuinely exist: Element on all three platforms, RustDesk and Claude Desktop on macOS and Windows, Podman, QEMU, WireGuard and FreeRDP with their Homebrew and winget counterparts. Where none exists the entry is honestly single-platform: LACT drives kernel GPU interfaces, Junction works through the XDG portal, Pods and gitg and GitY are GTK applications, and Distrobox builds on host integration that exists nowhere else. **MarkText and Organic Maps ship macOS and Windows builds but neither Homebrew nor winget packages them**, so there is no unattended install path and the entry says so rather than pretending.

**Two entries were dropped rather than guessed at.** Ghostty has no GitHub releases and no Linux repository this machine could name — its copy came from a downloaded `.deb` with no origin — and T3 Code has no identifiable upstream at all. Inventing a download URL for either would have produced an entry that fails on someone else's machine.

**The audit found three more detection bugs, all the same shape as Steam's** — an entry that knows one packaging and is blind to the others:

1. **Every flatpak entry misreported an app installed on two branches.** `flatpak info <id>` refuses to answer when both `master` and `stable` are present, exits non-zero, and detect concluded "not installed" — for software installed *twice*. The tool would then have offered a third copy. Presence is now asked of `flatpak list`, which is unambiguous; the update comparison is skipped when a single branch cannot be resolved, because "installed, and no update is being claimed" is the honest answer. **50 detect scripts rewritten.**
2. **`vm-manager` reported GNOME Boxes absent** while the flatpak was installed, because it only checked the apt package.
3. **`winboat` reported absent** while installed from its `.deb`, because the entry only knew the AppImage.

All three now recognise both packagings and remove whichever is present — an entry that can detect two packagings but remove only one makes unchecking silently do nothing.

That is the third distinct flatpak ambiguity this project has hit: **remotes** (flathub in two installations), **installations** (system and user), and now **branches**. Each produced a confident, wrong answer rather than an error, which is what made them expensive to find.

### Ideas taken from the established Windows debloat projects — 2026-09-03 (user's request)

Read `Raphire/Win11Debloat` (57k stars) and surveyed `ChrisTitusTech/winutil` (62k), `farag2/Sophia-Script`, `HotCakeX/Harden-Windows-Security` and `W4RH4WK/Debloat-Windows-10` for ideas. Win11Debloat's ~65 `.reg` files are the most directly useful: each is one named behaviour with the exact key, which maps cleanly onto this catalog's one-entry-per-behaviour model.

**Five adopted**, each chosen because the reason is concrete rather than "it is bloat":

- **Disable Windows Recall** — Recall snapshots the screen every few seconds and indexes it. Even held locally, that is a searchable record of every password and message that was ever on screen. Set in both the machine and user policy hives, since Windows honours whichever it finds.
- **Disable Fast Startup** — the one with the sharpest justification. Fast Startup leaves the filesystem hibernated rather than closed, so any partition shared with another operating system is locked or silently corrupted when that system writes to it. It also makes firmware settings unreachable, because the machine never truly powers off.
- **Disable update sharing** (Delivery Optimization `DODownloadMode=0`) — stops the machine seeding Microsoft's updates to strangers over the user's connection.
- **Remove web results from Start search** — every character typed into Start is otherwise sent to Bing as it is typed.
- **Disable location services** — machine-wide, so it covers every account.

**Deliberately not adopted**, and the reason matters as much as the list: the bulk of what those projects offer is *taste* rather than debloat — taskbar alignment, Alt-Tab entry counts, animation toggles, which folder Explorer opens in, Start menu layout. Shipping those would grow the catalog without making any machine better, and every one of them is a setting Windows already exposes in its own UI. This catalog's bar is "the reason can be stated in a sentence and the reversal is exact".

Also passed over: their **Edge and Brave tweaks** (browser configuration is the browser's business, and these reach into another vendor's product), and **`Disable_Bitlocker_Auto_Encryption`** — turning off disk encryption by default is the opposite of what the disk-encryption advisory recommends, and no entry here should quietly make a machine less safe.

All five follow the reversal rule already established: unchecking **deletes the policy value** rather than writing the opposite, handing the decision back to Windows' own default instead of forcing the feature on.

**An escaping bug was caught before commit**, worth recording because it would have failed only on a real Windows machine: the generated PowerShell had doubled backslashes in the registry paths — `HKLM:\\SOFTWARE\\Policies` where a single separator was needed. Bash collapses `\\` to `\` inside a double-quoted string, and PowerShell then received a path that no registry provider would resolve. Verified by asking bash to expand the fragment exactly as the script would: it now hands over `HKLM:\SOFTWARE\Policies\Microsoft\Windows\DeliveryOptimization`.

### 1.1 Catalog schema & loader
- [x] Define the on-disk layout, two separate top-level roots so entries and profiles never mix: `catalog/[category]/[kind]/[id]/[platform]/[operation].sh` for the four operations (`detect`/`install`/`remove`/`update`), plus a `catalog/[category]/[kind]/[id]/meta.toml` (name, description; `website` — required for `install`-kind entries specifically since a configure/cleanup entry like "disable telemetry" doesn't really have one, optional otherwise; `destructive` and `requiresElevation`, both optional booleans defaulting to false, added while building the plan engine in §1.5 since it needed exactly this per-entry information) one level up, shared across platforms; and `profiles/[name].toml` (§1.8) referencing catalog entries by their `[category]/[kind]/[id]` path. Any non-script asset an entry needs (a wallpaper image, an alias file) lives inside that same entry's directory — next to `meta.toml` if shared across platforms, or inside the specific `[platform]/` folder if platform-specific — never in a separate shared assets location, so an entry (and an override of it, §1.9) stays fully self-contained and portable on its own. Cause: `Deno.writeTextFile(path, ..., {append:true, create:true})`'s `create:true` only creates the *file*, never missing parent directories — on this user's genuine first-ever run, `~/.config/autoinstall/` didn't exist yet. **Second production bug, reported by the user: "I try to install terraform and it failed."** Root-caused from the real history log (`~/.config/autoinstall/history.jsonl`, which the crash fix above had finally made writable), not guesswork — it recorded the exact failure: `sudo: a terminal is required to read the password; either use the -S option to read from standard input or configure an askpass helper`.

Two independent real causes, both now fixed:

1. **Nothing ever acquired sudo credentials.** `src/elevation/` had `planRequiresElevation` and `startKeepAlive` built and tested since Phase 1, but *nothing called them* — no code path ever ran `sudo` at all, so an elevated plan just ran its scripts and let each one's own `sudo` fail. Added `src/elevation/session.ts` (`requestSudoAccess` = `sudo -v`, `startSudoKeepAlive` = the `sudo -n true` refresh loop on the existing `startKeepAlive`, `releaseSudoAccess` = `sudo -k`, all behind an injectable `SudoRunner` so tests never spawn a real sudo — 7 tests). Wired into both real execution paths: `App.tsx`'s `runPlan` and `main.tsx`'s `--yes` path each now ask **once, up front, only when the confirmed plan actually needs it** (PROJECT_DEFINITION.md §15), keep it alive for the run, and release it at the end; a declined prompt reports "not granted" and runs nothing rather than failing per-action. The TUI wraps the prompt in Ink's own `suspendTerminal` (verified against the installed ink@7.1.1 source — `App.js`'s `pauseInput`/`resumeInput`, `ink.js`'s `beginSuspend`/`endSuspend`) so sudo gets an uncontested terminal instead of racing Ink's raw-mode input loop.

2. **`setsid` was stripping the controlling terminal, which sudo needs.** This is the deeper cause, and fixing (1) alone would *not* have been enough. `runScript` runs every script under `setsid` (for the process-group timeout kill, see §1.3) — that creates a new session with **no controlling terminal**. Measured directly: a script run through the real `runScript` under a real pty reports `tty=?`, fails to open `/dev/tty`, and reproduces the user's exact error verbatim. It matters because sudo's credential cache is keyed by terminal — `man sudoers` confirms `timestamp_type` defaults to `tty`, falling back to parent-PID when no terminal is present — so a `setsid`-isolated script can *never* match a credential the main process cached, no matter how correct (1) is. Added an opt-in `preserveControllingTerminal` option to `RunScriptOptions`, which `runPlanAction` now sets exactly when `action.requiresElevation` is true; measured after the fix: `tty=pts/4`, `/dev/tty` opens. **A first attempted fix (`setsid -c`) was wrong and was reverted** — it fails with "Operation not permitted" because the terminal already belongs to the parent's session, and it took the script down with it (empty output, nothing ran). Caught by actually running it rather than reasoning about it.

Honest trade-off, measured and pinned by tests rather than glossed: the terminal-preserving path has no process group to kill, so a timeout can only kill the direct shell and any still-running descendant keeps the output pipe open — `timedOut` is still reported truthfully, but the run isn't actually cut short (a plain `sleep 5` under a 100ms timeout takes the full 5s). A separate process group would restore the kill guarantee but put the script in a *background* group, where sudo's prompt takes SIGTTIN and suspends instead of prompting — trading a timeout gap for a hang. Nothing passes `timeoutMs` for elevated actions today, so this costs nothing in practice; two tests pin both halves of the contrast so a future change can't silently regress either. Also fixed a latent hazard this surfaced: the timeout's group-kill (`kill -- -<pid>`) was gated on `usesProcessGroups` (platform) rather than on whether *this run* actually created a group — without the fix it would have signalled an unrelated process group, potentially this process's own.

**Phase 7 wiring — 2026-09-02.** Two of the three Windows-only modules were unreachable, and one of them was hiding a real defect.

**`exec/git-bash` was never called, which meant Windows could not run a single catalog script.** Every operation is a `.sh` file on Windows too, and `runScript` defaulted to a bare `bash` that is not on PATH on a stock Windows machine — so every detect and every install would have failed with a spawn error naming a binary the user has no reason to have. A new `exec/shell-resolution.ts` resolves Git Bash once per process (cached: the answer cannot change mid-run, and probing per entry across ~80 detects would be waste), and it is now threaded through **both** the diagnostic scan and the execution path in the TUI and the CLI. A missing Git Bash is surfaced as a notice rather than left to fail 80 times. 5 tests, including that the failure is cached too.

One subtlety worth recording: the shell is passed explicitly into `runDiagnosticsFor` rather than read from React state, because the scan runs during startup in the same tick as the `setState` — reading state there would have silently scanned with the wrong shell on Windows.

**`platform/wsl` was never called either**, so the §7 offer was never made. `startup/wsl-notice.ts` turns detection into an actionable message, kept pure so it is testable without a Windows box (5 tests). It is deliberately **advisory**: installing WSL reboots the machine and changes virtualisation settings, which is far beyond what belongs behind a confirm screen. It distinguishes four states, including the one that matters most — WSL present but with only non-Debian distributions, where silently assuming compatibility would produce a run in which nearly every apt-based entry fails.

`elevation/progress-protocol` remains unreachable. It exists for a Windows elevated-helper process that does not exist yet; wiring it would mean inventing the consumer, so it stays unused and is recorded as such.

## Phase 8 — Distribution & lifecycle

**Compile-to-binary spike — run 2026-09-01, and it found a real defect.**

`deno compile` itself works: `main.tsx` compiles cleanly with Ink/React bundled into a single ~110MB binary, no special flags beyond the permission set. That was never the risk.

**The defect**: `deno compile` resolves `new URL("../../catalog", import.meta.url)` to a *virtual* path inside the binary (`/tmp/deno-compile-<name>/catalog`). The first compiled binary therefore shipped with **no catalog at all** — it reported "catalog root does not exist" and could do nothing. Adding `--include ./catalog ./profiles` fixed the loading, and produced a subtler and much worse failure: the catalog loaded fine, and then **every single detect silently failed**, leaving an empty plan with no error shown. Cause, verified directly rather than inferred — `bash <embedded path>` reports "No such file or directory", and even a separate Deno process cannot read it: `--include` makes files readable by *the binary's own* Deno APIs, not by anything it spawns. Since every catalog operation runs as `bash <script>`, an embedded catalog is unrunnable.

This is a genuine collision between two deliberate project rules: "every operation is an individual script file, runnable standalone by hand" (PROJECT_DEFINITION.md §2) and "ship one self-contained binary" (this phase). Both are kept by extracting the embedded tree to a real directory under the config dir on startup (`src/startup/assets.ts`, wired into both entry points, a no-op when running from source so the working tree stays live during development). Extraction is unconditional rather than cached, so upgrading the binary can never leave a stale catalog behind.

**Verified end to end on a clean machine**: the binary was run inside a bare `ubuntu:24.04` container with **no Deno, no Node and no repository present**. It extracted all 249 scripts, ran the real detect scripts, and produced a correct plan — `jq` reported already-satisfied where installed, `Go` correctly planned an install where absent. That is the actual "ship it" scenario working.

A `deno task compile` now makes this repeatable, and four tests in `src/startup/assets.test.ts` pin the contract that matters: whatever root is returned must be readable by a *spawned process*, since that is precisely what the embedded path failed to be.

**Still open in this phase**: cross-compiling for macOS/Windows targets and verifying those binaries (unverifiable from this machine), checksum-verified bootstrap, and the release/signing process.
